**Fix has two separable parts, per the task framing — both required, sequenced:**

1. **Small, ships immediately.** Change the six-field stub (`db.js:1458-1464`) to return `null` (already-null-safe per the UI code above; the two structured fields — `supervisorNgramMatrix`, `methodologyConceptMatrix` — become `null` too, not their current empty-but-truthy shape, so the frontend's own `!data` guards catch them uniformly) and thread `source.aggregateSource`/`detailedAnalyticsRecordLimit` into each panel's empty-state message in `analytics-dashboard.js` (five call sites: the two above plus wherever `methodologyConceptMatrix`, `methodologyTopicMatrix`, and the ngram-cloud-adjacent term-cooccurrence panel each render their own "no data" branch). This alone satisfies the literal words of the gate for these panels — a rendered, explained absence, never a silent one indistinguishable from zero signal.

### #25 (M-01) — citation co-occurrence self-joins the full table, ignoring the caller's bounded sample

**Confirmed mechanism.** `getCitationCooccurrence(limit = 100)` (`db.js:4000-4026`) takes **no document-set parameter at all** — only an output-row `limit`. Its self-join (4013-4021, `dc1.doc_id = dc2.doc_id AND dc1.citation_id < dc2.citation_id`) takes no document-set bound. (Precise mechanism, verified by `EXPLAIN QUERY PLAN`: the planner actually drives from `top_citations` (≤50 rows), not a literal full-table scan — but the intermediate cardinality is still (documents containing each top citation) × (other citations in those documents), which grows with corpus size for any popular citation. So the covering indexes are used; the row count they are asked to join is what is unbounded.) `buildCitationCooccurrenceNetwork()` (`metrics.js:862-879`) calls it with a bare `100` and otherwise ignores the `records` array its own caller (`buildMetricsPayloadFromRecords`) is working from — so even when `/workbench/visualizations` has already bounded the rest of the payload to ≤5,000 sampled documents (`queryTopicDocumentPage`, `VISUALIZATION_DOCUMENT_LIMIT`), this one panel's cost is driven by the **total corpus's citation-table size**, not the sample. At 56,000 documents with, say, 30 citations/document, `document_citations` has ~1.68M rows; the self-join before the `HAVING shared >= 2` filter is O(rows²/citation) in the worst case and, per the issue's own estimate, tens of millions of intermediate rows — recomputed on every cache miss (`cachedSlice` in `metricsRoutes.js` keys on `sourceCacheKey(params)`+filters, so a filter change or cache eviction re-triggers the full unbounded join).

**Corrected: this is not an indexing problem.** As established in the status table above, both join arms already resolve to covering-index plans. **Fix, in the corrected order the issue's own three-part suggestion implies once the index question is settled:**
1. **Immediate, reuses existing infrastructure:** pass the same bounded document-id set the rest of `/workbench/visualizations`' payload is scoped to (`queryTopicDocumentPage`'s returned `page.documents` ids) into `getCitationCooccurrence` as a `WHERE dc1.doc_id IN (...)` (or a temp table / `json_each` on a bound array, since libsql's parameter-count ceiling makes a giant `IN (...)` list risky above a few hundred ids — bind via `WHERE dc1.doc_id IN (SELECT value FROM json_each(?))` with a single JSON-array parameter, which both SQLite and libsql support). This makes citation co-occurrence's cost consistent with every other panel's existing sampling contract (`documentsTruncated`, `aggregateSource: 'bounded-topic-document-page'`) instead of silently escaping it. This alone flattens response time between 5k and 56k, because the self-join's input is now the fixed sample size, not the corpus.
2. **Durable, shares infrastructure with #15's SQL-port work (§4):** materialize the full-corpus co-occurrence into a summary table (`citation_cooccurrence_summary(citation_id_a, citation_id_b, shared_count, computed_at)`), refreshed by a periodic job that scans `document_citations` once (per top-cited citation, this is the same "list co-occurring citations" computation, just run as a batch job instead of per-request). Serving then reads the summary table directly — O(1) relative to corpus size, and gives the panel full-corpus fidelity instead of the sample's fidelity. This is the more correct long-term answer (fix 1 alone means the panel forever reflects only a 5,000-doc sample of a 56,000-doc corpus) but requires new job-scheduling machinery (§4).

**Recommendation:** ship (1) immediately (small change, closes the "ignoring the bounded sample" defect literally and satisfies the flat-response-time verification on its own), land (2) as the durable fix once the shared refresh-job infrastructure exists (§3/§4 — the same job also produces #15's `termCooccurrence` summary and is the natural single piece of new infrastructure this phase needs).

### #26 (M-02) — term co-occurrence's threshold is corpus-size-blind, and its real exposure is worse than "below 5k only"

**Confirmed mechanism, exactly as filed:** `buildTermCooccurrence` (`metrics.js:559-625`) builds a `pairCounts` Map keyed by every unordered pair of (filtered, deduped, multi-doc) concept terms observed within a single document's term set (the nested loop at 580-585), across every record passed in. The `count >= 2` floor (line 589, comment: `// minimum co-occurrence (corpus is ~400 docs)`) is a fixed constant that does not scale with `N` (the `records.length`, captured as `N` at line 563 and used only for the `lift` statistic, never for thresholding).

**Where this is actually reachable — corrected and expanded from the filed framing.** The filed issue frames this as "currently only reachable below the 5k threshold." That is true for `/workbench/analytics`'s gated route, but this function is *also* invoked:
- Via `/workbench/visualizations` (always, on ≤5,000 sampled docs) — **wastefully**: `visualizationSlice` (`metricsRoutes.js:278-299`) never reads `termCooccurrence` out of the payload `buildMetricsPayloadFromRecords` returns, so every hit to this route computes a term-cooccurrence Map that is thrown away. Worth fixing regardless of #26/#15 (a cheap efficiency win — skip building it when the caller is the visualizations route), but not itself a scaling bug.
- Via `GET /api/metrics` (`metricsRoutes.js:706-825`) as an admin with an uncapped `maxRecords` — **this is #24's exposure**, and it is the one path where `N` is not held to any constant today. This is where the issue's own "~10.6M entries at 56k" estimate is actually reachable in the current code, and it ties #24 and #26 together more tightly than either filed issue states on its own (§4).

**Fix:** (a) scale the minimum-count threshold with `N` rather than hardcoding `2` — see §3 for the concrete formula recommendation and why it needs a product decision; (b) independently of the threshold, cap `pairCounts`' peak size directly (a per-document pair budget, or an early-eviction strategy keeping only a bounded top-K running set) so memory is bounded even before the threshold filter runs at the end — the threshold only shrinks the *output*, not the Map's peak occupancy while every document is being scanned, which is the actual OOM risk lever; (c) fix the stale comment. (b) matters independently of (a): even a well-scaled threshold does not prevent an unbounded `pairCounts` Map from being materialized in full before the filter is applied.

### #27 (M-03) — supervisor network wastes memory holding doc-lists for pairs that never make the graph

**Confirmed mechanism, exactly as filed.** `buildSupervisorNetwork` (`metrics.js:810-860`) builds `edgeMap` (811-840) with `e.docs.push(rec.id)` at line 837 for **every** co-authorship pair in **every** record, unconditionally. Only *after* the full scan does it compute `topNodes`/`topSet` (842-846) and filter `edgeMap`'s entries down to pairs where both endpoints are in the top 30 (850-853). Every non-qualifying edge's `docs` array was fully populated for nothing.

**Fix:** two-pass, per the task's own suggested design — pass 1 builds only `nodeMap` (drop `edgeMap`/`docs` entirely this pass), computes `topNodes`/`topSet`; pass 2 re-scans records and populates `edgeMap` (with `docs`) *only* for pairs where both endpoints are already in `topSet`. This changes the function from one records-scan that always pays O(all pairs) memory, to two records-scans that together pay O(records) time but only O(top-30-pairs) memory — a straightforward, low-risk restructuring that does not change the function's output (same top-30 nodes, same edges, same weights, same `docs` lists for the edges that survive).

**Same #24-exposure caveat as #26** (§4): today, `records.length` is held to ≤5,000 by `VISUALIZATION_DOCUMENT_LIMIT` on every route except the admin-only, currently-uncapped `/api/metrics`.

### #28 (M-05) — the entire OC record, potentially including full document text, is persisted into `source_json`

**Confirmed exactly.** `sync.js:646-656`:
```js
const batch = docs.slice(0, Math.max(0, source.maxRecords - totalSeen)).map((raw) => {
  const normalized = normalizeRecord(raw);
  return {
    doc: normalized,
    syncKey,
    source: { ...raw, sourceUpdatedAt: sourceUpdatedAt(raw) },
  };
});
```
`raw` is the untouched upstream OC hit. This full object (spread, plus one added field) is what `saveDocumentMetadata`/`saveDocumentMetadataBatch` receive as `source`, and `documentColumns` (`db.js:711`) does `sourceJson: source ? JSON.stringify(source) : null` — a byte-for-byte serialization of the entire upstream record into `documents.source_json`, alongside the already-normalized, much smaller `metadata_json` column.

**The zero-retention risk is real and unconditional on the code path, even though whether it fires in practice is unverifiable here.** `normalizeRecord` (`metrics.js:94-176`) explicitly knows how to read `full_text`/`FullText`/`transcript`/`text`/`ocr`/`body` off `doc` (line 111, `firstPresent(doc, [...])`) — proving the ingestion code was written with the expectation that at least some upstream records carry one of these fields. That value is used only to backstop a word-count estimate (`textForLength`, line 130) and is **not** stored on the returned normalized record — so `metadata_json` is safe. But `source_json`'s `JSON.stringify(source)` at `db.js:711` has no field-level filtering whatsoever: if `raw.full_text` (or any of the other four names) is present upstream, it rides into `source_json` verbatim, indefinitely, in every row. **Confirmed unable to verify from this sandbox whether OC actually populates any of these fields for UBC theses** — the outbound proxy blocks `oc-index.library.ubc.ca`, and no cached/fixture OC response in this repo answers the question either (test fixtures construct `normalizeRecord`'s output directly, never real upstream JSON with a `full_text`-shaped field). **The fix must not assume either answer — strip these fields from what gets persisted into `source_json` regardless of whether they are ever populated in practice**, exactly as the task brief directs.

**Recommendation (§3 spells out the confirm-with-user framing):** stop storing the full upstream record. Store a trimmed provenance subset instead — enough to satisfy whatever `source_json` is actually read for today (checked: `db.js:1908,1928` parse it back out only as an opaque `source` field attached to `sync_runs` rows for audit/debugging display, not for any analytics computation) — concretely `{ id, sourceUpdatedAt, retrievedAt }` plus (if genuinely needed for debugging) a byte length and a content hash of the original payload rather than the payload itself. Explicitly strip `full_text`/`FullText`/`transcript`/`text`/`ocr`/`body` even if a fuller provenance subset is kept, as defense in depth against the field showing up in the record shape unexpectedly.

### #24 (B-05 residual) — the admin path through `/api/metrics` has no ceiling, and is the on-ramp for #26/#27's worst case

**Confirmed exactly.** `metricsRoutes.js:754`: `const effectiveMaxRecords = isAdminRequest ? maxRecords : Math.min(maxRecords, PUBLIC_MAX_RECORDS);` — the anonymous branch is bounded (`PUBLIC_MAX_RECORDS`, `src/config.js:103`, default 300 in production); the admin branch is **not bounded at all**. `computePayload()` (778-819) calls `listCachedDocuments({ limit: effectiveMaxRecords, offset: 0 })` then `collectMetrics({ ...sourceOptions, cachedDocuments, ... })` (796-804), which runs `buildMetricsPayloadFromRecords` — **every JS aggregator this phase discusses** — over however many records `maxRecords` asked for, then serializes `documents: normalizedRecords.map(...)` (metrics.js:1081-1086) for the full record set via `res.json()` (line 824) synchronously.

**This route, not `/workbench/analytics`'s 5,000-record threshold, is the actual place all of #26/#27's (and, less directly, #25's) worst-case costs are reachable today**, because `/workbench/visualizations`' `VISUALIZATION_DOCUMENT_LIMIT = 5000` and `/workbench/analytics`'s `DETAILED_ANALYTICS_RECORD_LIMIT = 5000` both hold every other route's JS-aggregation cost to a fixed ceiling regardless of total corpus size — `/api/metrics` alone has no equivalent constant. See §4 for the full picture of how fixing #24 changes the severity calculus for #26/#27.

**Fix:** apply a hard server-side ceiling on `effectiveMaxRecords` regardless of `isAdminRequest` (e.g. reuse `VISUALIZATION_DOCUMENT_LIMIT`'s existing 5,000 constant, or introduce an admin-specific one slightly higher than the public cap but still bounded — a product decision, not purely technical, since `/api/metrics` is documented/legacy API surface some external tooling may depend on for a specific record count). Beyond the record-count ceiling, cap the `documents` array in the response and return a cursor/pagination signal for admins who need the full corpus, steering them toward `/api/workbench/documents` (the paged, already-scale-tested route — `test/metadataScaleServing.test.js`) for bulk access instead of a single synchronous JSON blob.

Do not treat (A) alone as a permanent answer — flag it in the DoD table (§5) as "closed with a disclosed sampling caveat, not full-corpus fidelity," distinctly from the five SQL-ported panels which get full-corpus fidelity immediately.

### #26 — the threshold-scaling formula

**Decision needed.** The current fixed `count >= 2` was tuned by inspection for a ~400-document corpus (per its own comment). A formula must (a) keep today's behavior at small scale (do not regress the panel's usefulness on the existing, already-tuned corpus), (b) grow meaningfully by 56,000. Two candidate shapes, both defensible:
- **Additive/sqrt-scaled:** `minCount = Math.max(2, Math.round(Math.sqrt(N / 400)))` — grows slowly (minCount=2 up to N≈1600, minCount≈12 at N=56,000), keeping the panel's character similar to today while still bounding output size.
- **Proportional:** `minCount = Math.max(2, Math.round(N / 2000))` — grows faster (minCount=28 at N=56,000), more aggressively trims low-signal pairs but risks the panel going sparse/empty for legitimately-narrow-but-real topic clusters.

**Recommendation:** the sqrt-scaled formula — co-occurrence significance conventionally scales sub-linearly with corpus size (this mirrors why `lift` rather than raw `count` is already used for ranking at line 608), and a milder threshold leaves more of the ranking work to the existing `lift`-based sort (613) rather than double-penalizing rare-but-genuine pairs via both a steep count floor and the lift ranking. This is a tuning choice with no objectively correct answer from code alone — flag for confirmation, and note that whichever formula is chosen, it should be a named, testable constant (not inline math) so §2.3's threshold-scaling test has a stable target.

### #28 — provenance subset, migration, and the policy call

**Recommendation (repeated from §1, consolidated here as the explicit ask):**
1. **Provenance subset to keep:** `{ id: <upstream identifier>, sourceUpdatedAt }` — and consider dropping `retrievedAt`, since `documents.synced_at` (a real column populated on every `saveDocumentStatement`, `db.js:592`) already records ingestion time at the row level, making a `retrievedAt` inside `source_json` duplicate data. This preserves everything `source_json` is actually read for today (an audit trail of *when* and *from what upstream state* a record was last synced — confirmed the only consumers, `db.js:1908,1928`, parse it back only for that kind of display, never for analytics computation).
2. **Explicit strip, regardless of provenance-subset design:** never carry `full_text`, `FullText`, `transcript`, `text`, `ocr`, `body` (or any key matching those names case-insensitively) into whatever is stored, even if a future change widens the provenance subset for some other reason. This is a standing invariant, not a one-time cleanup — add it as an assertion in `documentColumns`/`saveDocumentStatement` itself (a defensive filter at the write path), not only as a one-time migration, so a future upstream schema change that adds a new full-text-shaped field cannot silently reopen this.
3. **Migration for existing rows:** a one-time script (or an idempotent startup migration, matching this codebase's `ALTER TABLE ... ADD COLUMN` + backfill precedent at `db.js:590-614` and Phase C's `ensure_incremental_schema` idiom) that rewrites every existing `documents.source_json` row to the trimmed shape, dropping whatever the full record currently holds. Because the trimmed shape only needs three fields that are also present in `metadata_json`/`source_updated_at` for most rows, this migration is low-risk to run destructively (no data currently believed load-bearing is lost) — but confirm this belief against production before running it, since `source_json`'s current full-record shape is exactly the kind of "maybe something depends on it that isn't in this codebase" risk a destructive migration should not be run on unilaterally.
4. **What needs the user's explicit confirmation, clearly separated from the technical recommendation:** (a) that no external tooling/dashboard outside this repo reads `documents.source_json` expecting the full upstream record shape (the recommendation above assumes not, based on this codebase's own consumers, but this plan cannot see outside this repo); (b) sign-off to run a destructive migration against production `source_json` data, since it cannot be undone once the full records are overwritten; (c) whether the trimmed provenance subset above is sufficient for whatever operational/debugging use case originally motivated storing the full record, or whether a fourth field (e.g. a content hash, or a byte-length) should be added to retain *some* signal about what the full record contained without retaining the record itself.

### #24 — the admin ceiling value

**Decision needed.** A specific number: reuse `VISUALIZATION_DOCUMENT_LIMIT` (5,000, already load-bearing elsewhere in this exact phase) for consistency, or pick an admin-specific higher number (e.g. 10,000) reflecting that admins have a legitimate occasional need for a larger single-request slice than anonymous users. **Recommendation:** 5,000, for consistency with every other route in this phase and because `/api/workbench/*`'s paged routes (already scale-tested at 5,100+ documents, `test/metadataScaleServing.test.js`) are the correct tool for an admin who genuinely needs the full corpus — `/api/metrics` should be treated as a bounded/legacy convenience endpoint going forward, not a full-corpus-dump API. Flag for confirmation since this is a policy call about acceptable admin API behavior, not purely a technical one, and since `/api/metrics` may have external callers (documented API, a script, a dashboard) that currently rely on requesting more than 5,000 records in one call.

## 4. Cross-cutting: shared infrastructure and tighter coupling than the filed issues state

**#15's `termCooccurrence` (option B) and #25's citation summary table are the same kind of problem and can share one refresh job.** Both are "N-choose-2 pairs over per-document set memberships, safe to compute in a periodic batch scan of the whole corpus, not safe to compute per-request at 56k." A single new job type (following the existing in-process JS admin-job pattern — `runThemeRecomputeAdminJob`/`src/services/themeJobRunner.js`, dispatched via `src/jobWorker.js:81-82`'s `theme_recompute` branch, not the Python-subprocess `concept_rebuild` pattern, since both computations are pure SQL/JS aggregation with no ML dependency) can produce both `citation_cooccurrence_summary` and `term_cooccurrence_summary` in one pass, scheduled analogously to `concept_rebuild`'s existing daily cadence (`server.js`'s `scheduleDailyConceptRebuildJob` machinery is the pattern to extend, not reinvent). This is new infrastructure this phase needs to build (a new job type, a schedule, a status surface) — sizeable enough that it should land as the *durable* fix for both #25 and #15's `termCooccurrence`, after each issue's *immediate* mitigation (bounded self-join for #25, bounded-sample real data for #15) ships first.

**#24 is the actual gating factor for #26/#27's full severity — fix it first, or their fixes are provably unreachable at their worst case in current code.** As established in §1's #24 and #26/#27 sections: today, the *only* code path that can hand `buildTermCooccurrence`/`buildSupervisorNetwork` (and every other JS aggregator in `buildMetricsPayloadFromRecords`) an unbounded record count is `/api/metrics` as an admin with a large `maxRecords` — every other route already holds them to ≤5,000 via `VISUALIZATION_DOCUMENT_LIMIT`/`DETAILED_ANALYTICS_RECORD_LIMIT`. This means: **landing #24 first closes off the only currently-reachable unbounded path**, after which #26/#27's own fixes become "harden a fixed ≤5,000-record computation" rather than "prevent an unbounded blowup" — still worth doing (the 5,000 constant could rise later; #27's wasted-memory pattern and #26's stale threshold are real bugs on their own terms even at a fixed N), but the risk profile changes materially once #24 lands. **Sequence #24 before or alongside #26/#27, not after.**

**#15's five SQL-ported panels and #25/#26's summary-table infrastructure both touch `getDocumentServingAnalytics`'s `Promise.all` block (`db.js:1343-1399`) as the natural landing site** — the five new SQL aggregates slot in next to the existing `overall`/`yearCounts`/`themes`/`concepts`/`methodologies` queries in the same `Promise.all`, sharing the same `filters`/`qualifier` setup already established there. Land these together in one pass over that function rather than five separate small patches, to avoid re-deriving the filter-composition boilerplate five times.

**#28 is fully independent of the other five** — different table (`documents.source_json` vs. the serving/aggregation paths the other five issues touch), different code (`sync.js`'s ingestion path vs. `metrics.js`/`db.js`'s serving path), and no shared infrastructure need. It can land in parallel with everything else, gated only on the policy confirmations in §3.

**Top risks.**
- **The real production corpus size is unverified from this sandbox.** Every "56,000" figure in this plan and the filed issues is a target/estimate, not a measured current count. Get the real number (`SELECT COUNT(*) FROM documents`) before finalizing which scale the gate harnesses should actually exercise — a gate proven at a guessed 56k that the real corpus never reaches (or already exceeds) would be miscalibrated in either direction.
- **Whether OC actually returns `full_text`-shaped fields for UBC theses is unverified from this sandbox** (proxy blocks `oc-index.library.ubc.ca`). #28's design deliberately does not depend on the answer — strip regardless — but the *urgency* of the migration (are there rows today carrying multi-megabyte text blobs right now, or is this a purely theoretical exposure?) cannot be assessed without checking `SELECT MAX(LENGTH(source_json)) FROM documents` against production before deciding how urgently to schedule the migration.
- **#15's `termCooccurrence` decision (§3) is genuinely a product trade-off, not a technical one** — shipping the bounded-sample option without disclosing the sampling caveat clearly in the UI would reintroduce a subtler version of the exact problem this phase exists to close (a panel that looks complete but silently isn't). The UI text for this specific panel needs to say "sampled" distinctly from the other five panels' "not computed" language once #15 lands — conflating the two states in the frontend copy would undersell the five fully-fixed panels and oversell the one sampled panel.
- **#26's threshold formula and #24's ceiling value are both open decisions this plan recommends but does not unilaterally resolve** — if shipped with the recommended defaults without confirmation, revisit them once the real corpus-size figure (above) is in hand, since both formulas were reasoned about using the 56,000 estimate.
- **The shared refresh-job infrastructure (§4) is new machinery** (a job type, a schedule, a status surface) with no direct precedent in this exact shape — `theme_recompute`/`concept_rebuild` are the closest analogues but neither produces a cross-document pairwise summary table. Treat this as the highest-implementation-risk single piece of this phase and budget review time accordingly; it is also the one piece explicitly sequenced last (point 6 above) so its own risk does not block the other five issues' closure.
- **`saveDocumentMetadata`'s single write path (`db.js:909-939`) is shared by both single-document and batch ingestion** (`saveDocumentMetadataBatch`, `db.js:941-960`, confirmed to call the same `saveDocumentStatement` helper) — #28's fix and its defensive-filter addition only need to touch this one function, but any test coverage must exercise both call shapes (single and batch) since a future refactor could silently diverge them.
